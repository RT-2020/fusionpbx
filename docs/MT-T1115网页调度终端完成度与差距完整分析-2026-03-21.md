# MT-T1115 网页调度终端完成度与差距完整分析

## 1. 文档目的

基于以下三类证据，对当前 `app/basic_operator_panel` 的网页调度终端实现进行完整分析：

- 标准条款
- git 历史演进记录
- 当前代码实际状态

输出目标：

- 判断当前需求完成度
- 识别与标准要求的关键差距
- 解释这些差距是“最近回归”还是“历史上尚未完成”
- 给出后续改造优先级

说明：

- 本文中的“完成度”是工程实现完成度评估，不等同于正式第三方标准认证结论。
- 评估对象是网页调度终端整体，不仅看单个页面按钮是否存在，还看“前端识别 -> 后端执行 -> 页面反馈 -> 可验收显示”是否形成闭环。

## 3. 先给结论

### 3.1 一句话判断

当前网页调度终端处于“功能点存在较多，但标准闭环不足”的状态。

### 3.2 完成度结论

如果按“功能是否大体存在”来评估：

- 完成度约为 `65% ~ 75%`

如果按“标准条款能否稳定验收通过”来评估：

- 完成度约为 `45% ~ 55%`

差异原因：

- 很多按钮、页面、方法已经存在。
- 但“呼叫场景识别、差异化提示、监控动作执行链路、前后台统一状态模型”没有真正打通。

### 3.3 核心结论

当前最接近标准要求的部分：

- 旧监控面板的状态显示和监控操作
- 新 WebRTC 面板的急呼专项能力
- 新 WebRTC 面板的组呼/全呼/会议能力

当前离标准最远的部分：

- `5.5.3.8` 的“各种呼叫通过不同声、光提示及号码显示”
- `5.5.3.6` / `6.7.4.6` 的中继汇接完整闭环
- `5.5.3.1` / `6.7.4.1` 中强插、强拆、监听等监控能力在网页端的统一稳定执行

## 4. git 历史说明了什么

## 4.1 旧 Operator Panel 的监控能力是长期积累的

从 git 历史可以看出，旧 `Operator Panel` 上游很早就具备“转接、监听、活动通话控制”方向的能力：

- `10896c10a`：增加 eavesdrop 目的分机能力
- `fb1ace1d0`：增加活动通话转接到任意号码
- `07f532afa`：恢复拖拽呼叫和转接
- `91efee3b2`：修复活动呼叫 eavesdrop

结论：

- 旧链路不是临时拼出来的。
- 它天生更接近“监控台”范式，因此在“状态指示、监听、转接、强拆”等标准要求上基础更扎实。

- 更准确地说，是这部分从一开始就没有被完整工程化。

## 5. 当前系统的真实结构

### 5.1 实际上存在两套调度能力

#### 第一套：旧监控面板链路

链路：

- `index.php`
- `resources/content.php`
- `resources/classes/basic_operator_panel.php`
- `exec.php`

特点：

- 轮询刷新
- 看板式状态展示
- 更强的监控和通话控制能力

#### 第二套：新 WebRTC 调度链路

链路：

- `resources/jssip-client.js`
- `resources/dispatcher-control.js`
- `dispatcher_api.php`

特点：

- SIP 注册
- 来电弹窗
- 线路卡片
- 组呼全呼会议
- 紧急呼叫专项

### 5.2 这两套能力没有统一语义层

当前不存在一个统一模型去描述：

- 对象类型
  - 用户
  - 中继
  - 调度员
- 通话状态
  - 空闲
  - 振铃
  - 接通
  - 保留
  - 会议
  - 转接中
  - 被监控中
- 呼叫场景
  - 普通呼叫
  - 紧急呼叫
  - 中继呼叫
  - 人工接续
  - 自动中继
  - 转接来电
  - 监听支路
  - 强插支路

结果：

- 旧面板和新面板各自做了一部分。
- 但标准要求的是“统一可见、统一可操作、统一可验收”的调度终端。

- `5.5.3.1`
- `5.5.3.8`
- `6.7.4.1`

- 多会话有

## 8.2 按标准闭环验收度

如果看“是否形成可稳定验收的网页调度终端”，当前完成度更接近：

- 中继未闭环
- 转接来电识别未闭环

- 监控动作后台执行链路存在结构性风险

## 8.3 最合理的表述

最准确的说法不是：

- “已经基本完成”

也不是：

- “几乎没做”

最合理的表述应是：

- “关键能力已铺开，但离标准化闭环仍有明显差距；功能点存在度不低，验收闭环完成度偏低。”

## 9. 当前差距的根本原因

### 9.1 根因一：新旧两套能力没有统一模型

旧链路偏监控。

新链路偏 WebRTC 通话交互。

问题不是某个按钮没写，而是：

- 两套能力没有被统一成一个调度终端状态机。

### 9.2 根因二：最近开发重心偏急呼和会议，不是偏监控和中继

从 git 演进可以清楚看到：

- 近几轮核心投入是：
  - 组呼/全呼/会议
  - 急呼
  - 录音
  - SIP 注册

不是：

- 中继统一化
- 转接识别统一化
- 强插强拆链路标准化

### 9.3 根因三：控制路由没有为新场景重构

前端已经从旧面板升级到更多网页交互。

但 `exec.php` 这类底层执行入口没有同步按新场景做干净拆分。

结果：

- 上层功能越来越多
- 底层路由越来越混杂

## 10. 风险排序

### P0 风险

- `exec.php` 控制路由混杂，影响转接、监听、插入讲话等核心监控能力稳定性

### P1 风险

- 新面板不能识别“转接来电”和“中继来电”
- 直接导致 `5.5.3.8` 无法成立

### P1 风险

- 差异化声光提示只覆盖紧急呼叫
- 普通/转接/中继场景不可验收

### P2 风险

- 旧面板和新面板语义不一致
- 后续越补越容易重复开发和交叉打架

## 11. 最终判断

### 11.1 当前最接近的状态

如果现在就拿去做内部演示：

- 可以展示很多能力
- 看起来不像“未开发”

如果现在就拿去做标准导向验收：

- 风险较高
- 尤其会卡在：
  - 各种呼叫不同提示
  - 中继汇接闭环
  - 强插强拆监控动作的稳定性

### 11.2 对需求完成度的最终结论

建议统一采用下面这句结论：

- 当前网页调度终端对 MT-T1115 相关要求的实现，已经完成了大部分基础功能铺设，特别是状态显示、组呼全呼、会议、急呼、录音、SIP 注册等能力；但从标准验收闭环看，仍未完成“各种呼叫差异化提示、中继汇接闭环、转接场景识别、强插强拆执行链路稳定化、统一状态模型”这几项关键工作，因此整体应判断为“部分满足标准，距离完整满足仍有明显差距”。

## 12. 建议下一步

建议后续分析和实施按以下顺序进行：

1. 先修正 `exec.php`，把 `uuid_transfer`、`uuid_eavesdrop`、插入讲话等控制路由独立拆清。
2. 建立统一的呼叫场景模型，至少补齐：
   - 普通来电
   - 紧急来电
   - 中继来电
   - 人工接续来电
   - 自动中继来电
   - 转接来电
   - 监听支路
   - 强插支路
3. 在 `jssip-client.js` 中增加转接相关 SIP 头识别。
4. 在 `dispatcher-control.js` 中按 `scene` 而不是按 `isEmergency` 渲染提示和线路状态。
5. 最后再统一旧面板和新面板的状态、文案、按钮和验收口径。
