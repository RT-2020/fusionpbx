# 自研平台重写可行性评估（MT/T 1115-2011 最小功能集）

> 评估日期：2026-09-08
> 评估背景：用户提出"考虑从 0 重新开发一套系统，仅先要求实现 MT/T 1115-2011 标准所需功能"，原因是 FusionPBX 作为开源产物"不太可控"。
> 已澄清的约束：核心痛点 = **部署困难，必须依赖官方安装脚本**；倾向方案 = 保留 FreeSWITCH、重写平台+调度台；资源 = **1 人（可能兼职）**；终端制式 = WiFi + SIP。

---

## 1. 结论先行

| 路线 | 内容 | 工作量 | 解决部署痛点 | 风险 |
|---|---|---|---|---|
| **L0 容器化/固化部署** | 不重写代码，把现有 FusionPBX+FreeSWITCH 的部署链路固化成 Docker 镜像或 Ansible playbook | **1~3 周** | ✅ 彻底解决 | 低 |
| **L1 渐进剥离（绞杀者模式）** | 先 L0 止血；再逐步用自研服务替换 FusionPBX 管理面（调度台前端平移、Lua 脚本保留） | 6~18 个月，可随时停在任意中间态 | ✅（分阶段） | 中 |
| **L2 一次性全量重写** | 新起仓库，一次性重写管理平台+调度台后端 | 1 人全职 **10~16 个月** MVP；兼职 **2~3 年** | ✅ | 高 |

**推荐：先做 L0（立刻消除痛点），再以 L1 作为长期演进路径；不建议直接 L2。**

理由：

1. 澄清后的痛点只是"部署难"，而部署难的根源已经定位清楚（见 §4），它**不是架构问题**，是"代码即部署 + 路径硬编码 + 官方脚本不在仓库"的工程化缺失，1~3 周可以固化解决；
2. 现有系统对标准条款的覆盖度已经很高（按 2026-03 推进文档，调度终端条款处于"阶段 5 待现场联调验收"），全量重写会把这部分进度**重置归零**；
3. 1 人兼职的资源做 L2，意味着 2~3 年内系统处于"两套都不完整"的中间态，期间现场交付、验收、故障响应都受影响；
4. 重写并非从零开始——已有大量可平移资产（§3），如果未来确要自研，L1 路线能把这些资产逐块搬走，且每一步都有可回退的稳定态。

## 2. 标准功能 → 平台需求映射（软件承担部分）

MT/T 1115-2011 全文已提取（`D:\工作空间-文件\KT135无线通信系统\mtt1115-提取文本.txt`）。5.5 节功能要求按承担方拆解：

### 2.1 硬件/无线制式承担（平台软件做不了，只配合）

防爆（GB 3836）、发射功率、接收灵敏度、移动台电池续航（≥11h/通话 2h）、基站备电 2h、脱网直通、越区切换的空口部分、移动台低电压报警。

WiFi+SIP 制式下的落地说明：

- **越区切换**（5.5.1.7，应）：WiFi 漫游 + SIP 重注册，FreeSWITCH 原生支持，平台只需正确配置；
- **脱网直通**（3.19，宜）：取决于终端硬件是否支持 WiFi 直通/Mesh，平台无关；
- **分布管理**（3.10，宜）：取决于基站硬件是否内置本地 SIP 能力，平台只能配合；
- **位置登记**（3.11，宜）：WiFi 下 = SIP 注册位置（接入点/基站），现有系统已有 registrations 展示。

## 3. 现有资产盘点（若选择自研路线，重写的真实起点不是零）

依据对 `app/basic_operator_panel`（约 2.3 万行）及部署链路的代码盘点：

### 3.1 可近乎原样平移（价值最高）

- `resources/jssip-client.js` + `jssip.min.js`（2330 行）：WebRTC/SIP 调度软终端核心，仅依赖浏览器 API，零后端耦合；
- **SIP 头"场景协议"**（X-Call-Scene、X-Monitor-*、X-Emergency-* 等 18 个自定义头）：前后端契约，语言无关，是整个调度台的语义骨架；
- `resources/dispatcher-control.js`（4069 行）绝大部分、`dispatcher.css`（2127 行）、`emergency-audio.js`、`dispatcher-logger.js`、`dispatcher-utils.js`：可带走 70%~95%；
- **FreeSWITCH 侧 Lua 业务脚本全家桶**（ring_groups / ivr_menu / voicemail / call_forward / conference_center 等，位于 `app/switch/resources/scripts/`）：保留 FreeSWITCH 即可原样继续用，只需维持 `v_extensions` 等表结构兼容。

### 3.2 知识可复用、代码需翻译（约 4000~5000 行 PHP 的等价重写）

- `dispatcher_api.php`（3259 行，30+ action）/ `exec.php` / `operator_panel_recording.php` 沉淀的 ESL 命令拼装全集：监听 eavesdrop、强插双腿入会、uuid_broadcast 录音、急呼 originate（Alert-Info 自动应答）——纯 FreeSWITCH 知识，与语言无关；
- YX02S 声光报警器 TCP 帧协议（`emergency_alarm_device.php`，753 行）：帧格式 + checksum 已调通；
- `emergency_alarm_service.php`（1149 行）的守护模式设计：ESL 事件监听 + DB job 表 + presence 对账 + 恢复补偿。

### 3.3 必须重写

- 管理面：用户/权限、分机、中继网关、会议、系统设置等 CRUD 与配置下发（现有 = FusionPBX 77 个 app 模块，重写可收窄到约 10 个域）；
- `index.php` 页面骨架（3585 行，PHP session + 权限条件渲染 + 内嵌 JS，最大耦合点）；
- `content.php` 的"服务端渲染 HTML 整段替换轮询"（1.5s/5s/10s 三层）——重写时应改为 JSON + 事件推送；
- CDR 入口（现 xml_cdr.service 落盘轮询模式）。

### 3.4 顺带应修复的已知问题（无论选哪条路线）

- 分机密码明文 JSON 注入页面（`index.php:146-152, 1281`）；
- 硬编码备用账号 5001-5003/密码 1234（`index.php:1309-1331`）；
- 大量 console.log / error_log 调试残留；
- HTML 整段替换轮询导致的状态闪烁。

## 4. "部署难"的根源与 L0 解法

### 4.1 根源（已逐一定位到代码）

1. **代码即部署**：无迁移文件，schema 靠运行时扫描 `app_config.php` diff 建表；`app_defaults.php` 既是数据种子又是系统级安装器（写 `/etc/freeswitch`、复制 Lua 脚本、chown、systemctl）；
2. **两段式安装**：第一段是外部仓库 `fusionpbx-install.sh`（不在本仓库，无法版本锁定、离线复现）；第二段是 Web 向导 `core/install/install.php`（内含硬编码 `php /var/www/fusionpbx/...` 的 shell_exec）；
3. **根路径硬编码面广**：`/var/www/fusionpbx`、`/etc/freeswitch`、`/usr/share/freeswitch/scripts` 散布在 switch_files.php、vars、save_* 系列中；PHP 与 Lua 双语言各有一份 config.conf 解析器；
4. **运行时与源码同机**：升级 = 对 docroot `git pull` + upgrade.php，天然排斥不可变部署；
5. **整机 13+ 进程、root/www-data/freeswitch 三用户权限交织**：9 个 systemd 服务（xml_cdr、email_queue、fax_queue、websockets、active_calls、active_conferences、system、event_guard、emergency_alarm）+ nginx/php-fpm/PG/FreeSWITCH。

### 4.2 L0 解法（1~3 周量级）

真正的运行时依赖面很窄：config.conf、PG 连接、ESL TCP 8021、对 `/etc/freeswitch` 的写权限、若干共享目录（recordings/voicemail/storage/log）。固化方案二选一：

- **Ansible playbook**：把部署动作表（安装包 → config.conf → upgrade.php -s/-d/-m/-p → 服务注册 → 权限）固化为幂等剧本，版本锁定，贴近现状；
- **Docker 镜像**：单容器（php+nginx+freeswitch+supervisor）或双容器（app 与 freeswitch 共享 volume：`/etc/freeswitch`、`/usr/share/freeswitch/scripts`、录音/CDR 目录）。FreeSWITCH 官方有现成 deb 源与容器实践，mod_lua XML handler 模式在容器内无障碍。

仓库内目前**没有任何容器化尝试**（无 Dockerfile/compose/ansible/CI），这是一个尚未开采的洼地。

范围：标准最小功能集（§2.2 全部 + §2.3 按需），保留 FreeSWITCH 与 Lua 脚本，调度台前端平移。

工期（假设熟悉本仓库全部上下文、使用现代框架与 AI 辅助编码）：

- **1 人全职**：MVP 10~16 个月，其中编码约 60%、现场联调与标准试验项（6.7 全套）验收约 40%；

## 6. 风险清单（按路线）

**公共风险**
- 现场联调验收从未系统完成（`MT-T1115新版WebRTC联调执行记录` 未回填）——无论哪条路线，这都是第一个该做的事；
- 组呼/全呼"实时、等待、中断"三模式、急呼"优先排队/中断"两模式的并发语义（标准 3.14~3.17）目前未完整产品化，重写与改造都要专门设计；
- 单人巴士因子：1 人持有全部系统知识，需要文档化（现有 docs/ 惯例很好，应延续）。

**L2 特有风险**
- 进度重置：调度台已到"阶段 5 待验收"，重写后重新联调；
- 2~3 年双系统并行期（兼职情形）；
- 新平台自身的稳定性爬坡（7 天稳定性试验、录音不丢、告警不漏）。

**许可证说明（澄清"开源不可控"）**
FusionPBX 为 **MPL 1.1**（文件级弱 copyleft）：允许商用、允许与闭源代码组合；仅修改过的 MPL 文件在**分发**时需向接收方披露源码。自研新模块可完全闭源。因此"合规上必须重写"的结论**不成立**；若客户提出代码自主性要求，L1 渐进路线同样能满足（新增代码全部闭源自有）。

---

## 7. 决策建议

1. **立即做 L0**：以 1~3 周代价消除"部署难"这个唯一明确痛点，产出 Docker 镜像或 Ansible playbook，版本锁定、离线可复现。这一步无论后续选什么都不亏。
2. **补完验收**：按 `MT-T1115新版WebRTC联调验收清单` 执行现场联调并回填记录，把"已完成开发"变成"已验收"。这是标准合规的真正短板。
3. **以 L1 为长期路径**：若确要自研（如产品化交付、代码自主性诉求），按绞杀者模式逐块替换——先在 FusionPBX 旁边立起新平台的调度台前端（平移 jssip 资产），再逐步接管管理面；每块迁移完成后旧模块退役，全程存在可回退的稳定态。
4. **不建议 L2**：在"痛点=部署"与"1 人兼职"两个约束下，一次性全量重写的收益/成本比明显劣于 L0+L1。
