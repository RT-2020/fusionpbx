# MT-T1115 新版 WebRTC 实体状态落地说明

## 1. 本轮落地范围

本轮只在新版 WebRTC 调度台上补齐“用户 / 中继状态指示”能力，不处理旧版 FusionPBX 调度交互。

涉及文件：

- `app/basic_operator_panel/dispatcher_api.php`
- `app/basic_operator_panel/resources/dispatcher-control.js`
- `app/basic_operator_panel/resources/dispatcher.css`
- `app/basic_operator_panel/index.php`

## 2. 已补齐的能力

| 能力点 | 本轮实现 | 代码位置 |
| --- | --- | --- |
| 用户状态快照 | 聚合分机静态信息、注册态、活动通话态，输出 `idle / ringing / busy / held / offline` | `dispatcher_api.php` `get_entity_status_snapshot` |
| 中继状态快照 | 聚合网关配置、`sofia xmlstatus gateway` 运行态、活动通话态，输出 `idle / ringing / busy / held / offline / error / disabled` | `dispatcher_api.php` `get_entity_status_snapshot` |
| 状态总览面板 | 页面新增“用户 / 中继状态”面板，展示汇总、告警、更新时间 | `index.php`、`dispatcher.css` |
| 对象级监控入口 | 在用户 / 中继卡片上直接提供 `监听 / 强插 / 强拆` 操作 | `dispatcher-control.js` |
| 状态自动刷新 | 前端轮询状态快照，注册成功 / 注销 / 注册失败后强制刷新 | `dispatcher-control.js` |
| 降级保护 | 当注册源 / 网关运行态源不可用时，不再误判为离线，降级显示告警与 `unknown` | `dispatcher_api.php`、`dispatcher-control.js` |

## 3. 新增状态模型

### 3.1 用户实体

后端按分机聚合以下信息：

- 分机号
- 别名
- 显示名称
- 用户状态 `user_status`
- 注册状态 `registered`
- 当前实体状态 `entity_state`
- 当前主通话 `current_call`
- 活动通话数量 `active_call_count`

### 3.2 中继实体

后端按网关聚合以下信息：

- 网关 UUID / 名称
- Profile / Proxy
- 启用状态 `enabled`
- 运行状态 `runtime_state`
- 当前实体状态 `entity_state`
- 当前主通话 `current_call`
- 活动通话数量 `active_call_count`

## 4. 对标准条款的提升点

| 条款要点 | 本轮前 | 本轮后 |
| --- | --- | --- |
| 用户或中继状态指示 | 主要是会话状态，不是对象状态 | 已具备对象级状态面板 |
| 用户状态明了 | 只能看到活跃会话，不能看全量对象忙闲态 | 可看到分机注册态、忙闲态、振铃态、保持态、离线态 |
| 监控操作便捷 | 主要从会话卡片触发 | 可直接从用户 / 中继状态卡片触发监听、强插、强拆 |

## 5. 仍然存在的差距

| 差距点 | 当前状态 |
| --- | --- |
| 监听链路便捷性 | 监听仍然不是完全闭环自动接入，便捷性弱于强插 |
| 强拆闭环 | 当前强拆仍以目标双腿 UUID 为主，强插后会议腿清理还不够彻底 |
| 中继识别准确性 | 仍部分依赖通道命名和网关运行态，服务端统一 `X-Call-Scene / X-Trunk-*` 标记还可继续加强 |
| 状态来源可靠性 | 当 ESL、注册状态或网关运行态任一来源不可用时，面板会降级并提示，但不是完全无损 |

## 6. 当前判断

本轮之后，新版 WebRTC 调度台已经从“场景化会话提示”推进到“对象级状态指示 + 对象级监控操作”。

对 MT-T1115 相关条款而言，最大的缺口已经不再是“没有状态面板”，而是：

- 监控闭环还需继续收尾
- 中继识别和状态源稳定性还可继续加强
