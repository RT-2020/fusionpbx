# MT-T1115 新版 WebRTC 功能对比分析

## 1. 分析范围

本文件只分析新版 WebRTC 调度实现，不再把旧版 FusionPBX Operator Panel 计入完成度。

新版范围：

- `app/basic_operator_panel/resources/jssip-client.js`
- `app/basic_operator_panel/resources/dispatcher-control.js`
- `app/basic_operator_panel/dispatcher_api.php`
- `app/basic_operator_panel/index.php` 中新版调度区域
- `app/basic_operator_panel/resources/emergency-audio.js`

不纳入本次结论：

- `resources/content.php`
- `resources/classes/basic_operator_panel.php`
- 旧版拖拽面板、旧版状态块、旧版 Operator Panel 交互

## 2. 先给结论

如果明确“后续只在新版上继续做”，那么当前新版的完成度判断应为：

- 按功能点存在度：`55% ~ 65%`
- 按标准闭环验收度：`35% ~ 45%`

原因：

- 新版已经具备浏览器 SIP 调度台的主骨架
- 但标准要求里最难的部分，尤其是：
  - 用户/中继状态指示
  - 各种呼叫差异化声光提示
  - 中继汇接闭环
  - 强插/强拆/监听的稳定链路
  主要还没有在新版里完整闭环

## 5. 新版当前最大的缺口

## 5.1 缺口一：新版没有完整的“用户/中继状态指示”

当前新版有：

- 调度员注册状态
- 当前 session 状态
- group/conference 状态栏

代码证据：

- `dispatcher-control.js:2224-2255`
- `index.php:948-1010`
- `index.php:1305-1312`

但标准要的不是这些，而是：

- 用户忙/闲状态
- 用户振铃状态
- 中继状态
- 用户或中继对象的可见状态指示

新版缺的东西：

- 没有完整用户列表状态面板
- 没有统一中继对象状态面板
- 没有“用户态”和“通话态”分层展示

结论：

- 新版当前只能算“会话控制台”，还不能算“标准意义上的调度监控台”

## 5.2 缺口二：新版没有完成“各种呼叫不同声光提示”

当前新版只真正区分了：

- `emergency`
- `normal`
- `conference`
- `eavesdrop`
- `three-way`

代码证据：

- `jssip-client.js:239-256`

实际 UI 提示只对急呼有独立能力：

- `dispatcher-control.js:596-605`
- `dispatcher-control.js:1163-1189`
- `emergency-audio.js:40-124`

缺失的场景：

- 普通内部来电
- 转接来电
- 中继来电
- 人工接续来电
- 自动中继来电
- 咨询转接支路

结论：

- 新版现在不满足 `5.5.3.8` 最核心的一句话

## 5.3 缺口三：新版没有完成中继汇接主流程

虽然有中继逻辑：

- `dispatcher-control.js:936-1118`

但主来电入口：

- `dispatcher-control.js:558-610`

并没有把来电真正识别成“中继呼叫”后切换进中继处理分支。

所以现在的状态更准确地说是：

- “写了中继处理方法”
- 不是“实现了中继汇接能力”

## 5.4 缺口四：新版没有完整接住强插 / 强拆 / 监听

从标准角度，新版最弱的一块不是急呼，不是组呼，而是监控调度能力。

现在新版有：

- `three-way`
- `eavesdrop`

这两个类型名

代码证据：

- `jssip-client.js:239-252`

但它们并没有形成完整、可验收的新版主链路能力：

- 没有独立监控台入口
- 没有明确目标用户状态和被监控状态显示
- 没有稳定的后台执行闭环

结论：

- 新版当前不能单独支撑“强插、强拆、监听等功能实施监控”这条标准要求

## 6. 新版有哪些“看起来有，但实际没闭环”的功能

| 功能 | 代码里是否存在 | 为什么还不能算完成 |
| --- | --- | --- |
| 中继模式 | 是 | 只有 UI 和方法，主来电流程未分流 |
| 转接 | 是 | 只有发起 REFER 和本地“转接中”状态，没完成业务级确认和来电识别 |
| 录音 | 是 | 主要是急呼触发，缺少统一录音状态体系 |
| 监听 / 插入讲话 | 部分存在 | 没形成新版主链路的稳定监控能力 |
| 多路呼叫 | 是 | 多 session 解决技术并发，不等于业务并发语义完成 |

## 7. 如果只在新版上继续做，最合理的需求补齐顺序

| 优先级 | 目标 | 为什么先做 |
| --- | --- | --- |
| `P0` | 建立新版统一状态模型：`对象状态 + 通话状态 + 呼叫场景` | 不先统一模型，后面每个功能都要返工 |
| `P0` | 在 `jssip-client.js` 补全来电场景识别，至少补中继/转接 | 不识别场景，就无法做不同提示 |
| `P0` | 在 `dispatcher-control.js` 把来电渲染改成按 `scene` 分流 | 这是新版满足 `5.5.3.8` 的前提 |
| `P1` | 打通中继主流程 | 这是标准硬要求，不是锦上添花 |
| `P1` | 给普通/转接/中继/急呼做独立声光提示矩阵 | 这是标准直指要求 |
| `P1` | 把监控能力迁入新版主链路：监听、强插、强拆 | 这是调度终端的核心，不补不成 |
| `P2` | 统一录音和扬声状态展示 | 便于验收和后续维护 |

## 8. 最终判断

如果你已经决定“旧版先不处理，直接在新版上继续”，那新版现在适合承担什么角色，结论如下：

### 8.1 新版适合继续作为主线

因为它已经具备：

- 浏览器 SIP 调度台骨架
- 急呼主链路
- 组呼/全呼/会议主链路
- 线路卡片和 session 管理基础

### 8.2 但新版还不适合直接宣称满足标准

因为它目前最大的问题不是“缺一个按钮”，而是缺：

- 调度终端状态模型
- 中继和转接场景识别
- 全场景差异化提示
- 完整监控调度链路

### 8.3 一句话结论

新版可以继续做，而且应该作为唯一主线继续做；但必须明确：

- 现在新版只是“网页 SIP 调度台骨架已成型”
- 还不是“已完整满足 MT-T1115 调度终端要求的网页调度终端”
