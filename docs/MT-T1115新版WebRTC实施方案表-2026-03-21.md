# MT-T1115 新版 WebRTC 实施方案表

## 1. 方案前提

本方案基于以下前提：

- 后续需求只在新版 WebRTC 调度实现上继续完成
- 旧版 FusionPBX Operator Panel 先不再扩展新需求
- 旧版仅作为参考语义和过渡期兜底，不作为主改造对象

新版范围：

- `app/basic_operator_panel/resources/jssip-client.js`
- `app/basic_operator_panel/resources/dispatcher-control.js`
- `app/basic_operator_panel/resources/emergency-audio.js`
- `app/basic_operator_panel/dispatcher_api.php`
- `app/basic_operator_panel/exec.php`
- `app/basic_operator_panel/index.php` 中新版调度 UI 区域

## 2. 总体策略

| 项目 | 决策 |
| --- | --- |
| 主业务前端 | 保留新版 WebRTC 调度台 |
| 旧版处理原则 | 不删除，不继续扩展，不作为主产品面 |
| 标准补齐方式 | 把旧版成熟“语义”迁移到新版，不把新版能力回灌旧版 |
| 本轮目标 | 让新版从“网页 SIP 调度台骨架”升级到“可对齐 MT-T1115 的网页调度终端” |

## 4. 新版统一状态模型

## 4.1 对象状态模型

| 字段 | 含义 | 取值建议 | 说明 |
| --- | --- | --- | --- |
| `entity_type` | 对象类型 | `dispatcher` / `user` / `trunk` | 先把“用户”和“中继”从一开始分开 |
| `entity_id` | 对象唯一标识 | 分机号 / 中继标识 / 会话侧对象 ID | 页面渲染主键 |
| `display_number` | 页面展示号码 | 分机号 / 来电号 / 中继号 | 用于标准中的“号码显示” |
| `display_name` | 页面展示名称 | 用户名 / 中继名 / 显示名 | 用于列表和弹窗 |
| `entity_state` | 对象状态 | `offline` / `idle` / `ringing` / `busy` / `held` / `monitoring` / `unknown` | 这是“用户或中继状态指示”的核心 |
| `state_source` | 状态来源 | `sip_session` / `server_snapshot` / `manual_mode` | 便于后续统一调试 |

## 4.2 会话状态模型

| 字段 | 含义 | 取值建议 |
| --- | --- | --- |
| `session_id` | 会话 ID | JsSIP `_customId` |
| `session_state` | 会话状态 | `incoming_ringing` / `outgoing_trying` / `connected` / `held` / `transferring` / `ended` |
| `direction` | 呼叫方向 | `incoming` / `outgoing` |
| `is_monitored` | 是否监控态 | `true / false` |
| `is_recording` | 是否录音中 | `true / false` |
| `is_emergency` | 是否急呼 | `true / false` |

## 4.3 呼叫场景模型

这是新版补齐标准的关键。

| `scene` | 含义 | 优先级 | 是否必须独立提示 |
| --- | --- | --- | --- |
| `normal_in` | 普通内部来电 | 中 | 是 |
| `normal_out` | 普通外呼 | 中 | 否，主要体现在线路卡片 |
| `emergency_in` | 紧急来电 | 最高 | 是 |
| `trunk_in_manual` | 人工中继来电 | 高 | 是 |
| `trunk_in_auto` | 自动中继来电 | 高 | 是 |
| `blind_transfer_in` | 盲转进线 | 高 | 是 |
| `attended_transfer_in` | 咨询转接进线 | 高 | 是 |
| `consult_leg` | 咨询转接中间支路 | 中 | 是 |
| `eavesdrop_leg` | 监听支路 | 中 | 是 |
| `barge_leg` | 强插 / 插入讲话支路 | 高 | 是 |
| `conference_invite` | 会议/组呼邀请支路 | 中 | 是 |

## 5. 新版场景识别规则表

## 5.1 `jssip-client.js` 场景识别扩展

当前位置：

- `resources/jssip-client.js:188-292`

建议把当前 `_callType` 粗分类扩展为 `scene` 精分类。

| 场景 | 识别依据 | 当前是否支持 | 需要新增 |
| --- | --- | --- | --- |
| `emergency_in` | `Alert-Info` / `X-Emergency-Call` / `X-Emergency-Uuid` | 是 | 保留并标准化输出 |
| `conference_invite` | 现有 `conference` / `group-call` 规则 | 部分 | 输出统一 `scene` |
| `eavesdrop_leg` | 现有 `Eavesdrop` / `Listen` 规则 | 部分 | 输出统一 `scene` |
| `barge_leg` | 现有 `ThreeWay` / `Barge` 规则 | 部分 | 输出统一 `scene` |
| `blind_transfer_in` | `Refer-To` / `Referred-By` / `Diversion` | 否 | 新增 |
| `attended_transfer_in` | `Replaces` / `History-Info` / `Referred-By` | 否 | 新增 |
| `trunk_in_manual` | 中继号码规则 / trunk 标记 / server side 标识 | 否 | 新增 |
| `trunk_in_auto` | 中继来电 + auto trunk mode | 否 | 新增 |
| `normal_in` | 上述都不命中 | 部分 | 作为兜底场景 |

## 11. 新版最终实施建议

如果只在新版上继续做，最合理的执行顺序不是先加零散按钮，而是：

1. 先补 `scene` 模型
2. 再补提示矩阵
3. 然后打通中继
4. 再补监控能力
5. 最后统一录音与显示状态

否则会出现的问题是：

- 每补一个需求都要返工前面的 UI 和状态判断
- 最终仍然会回到“急呼是一套逻辑、中继是一套逻辑、转接是一套逻辑”的碎片状态

## 12. 一句话结论

如果确认旧版暂不处理，那么新版应该继续做，而且必须按“统一状态模型 -> 场景识别 -> 提示矩阵 -> 中继闭环 -> 监控闭环”的顺序推进，不能再按零散功能点补丁式叠加。
