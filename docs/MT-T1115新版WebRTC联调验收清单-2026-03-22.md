# MT-T1115 新版 WebRTC 联调验收清单

## 1. 目的

把 `T10` 从“只有场景列表”落成“可直接执行、可回填结果、可复用回归”的联调清单。

本文档只面向当前新版 WebRTC 调度台，不覆盖旧版调度面板。

## 2. 当前适用范围

当前工作区已完成的重点改造包括：

- 统一 `scene / entityType / sessionState` 场景模型
- 差异化来电提示与线路卡渲染
- 人工 / 自动中继主流程
- 监听自动接入补齐
- 强插后强拆补齐会议腿清理
- 对象级状态面板
- 来电卡 / 线路卡上的录音态、监控态标识

因此本轮联调重点不再是“功能是否存在”，而是：

- 主链路是否稳定
- 页面状态是否与实际行为一致
- 失败时 UI 是否能正确回落

## 3. 联调前置条件

执行前至少确认以下条件：

1. 调度员网页已能完成 SIP 注册。
2. 至少准备 3 个可用分机。
3. 至少准备 1 个可用中继 / 网关。
4. FreeSWITCH ESL 可用，`show channels as json` 可正常返回。
5. `exec.php` 可执行 `uuid_record`、`uuid_kill`、相关 originate/bridge 命令。
6. 浏览器已允许麦克风，自动播放限制已解除。
7. 当前代码已部署到待联调环境，而不是只存在本地工作区。

建议最小测试对象：

- 调度员分机 `A`
- 普通用户分机 `B`
- 普通用户分机 `C`
- 外线 / 网关 `T`

## 4. 证据留存要求

每个场景至少保留以下证据之一：

- 页面截图
- 浏览器控制台关键信息
- `dispatcher_api.php` 返回结果
- FreeSWITCH `show channels as json` 或相关 `uuid_*` 执行结果

建议每个场景记录：

- 执行时间
- 执行人
- 环境
- 结果：`通过 / 失败 / 阻塞`
- 问题编号

## 5. 执行记录模板

每个场景执行完成后，按下列模板回填：


## 6. 联调清单

### S01 普通内部来电

前置条件：

- 分机 `B` 可呼叫调度员分机 `A`

执行步骤：

1. 用 `B` 呼叫 `A`
2. 观察新版来电卡
3. 观察新版线路卡
4. 在网页端点击接听
5. 挂断通话

预期结果：

- 来电卡显示普通来电样式，不出现急呼 / 中继 / 监控标识
- 号码、名称、接听 / 拒绝按钮正常
- 接听后线路卡显示“已接通”
- 挂断后线路卡和来电卡都清理干净

重点证据：

- 来电截图
- 接通后线路卡截图

### S02 急呼被叫接入

前置条件：

- 可从目标分机向调度员发起急呼

执行步骤：

1. 从目标分机向调度员发起急呼
2. 观察网页端是否出现紧急告警
3. 观察是否可执行“中断并接听”
4. 在网页端接听
5. 观察接听后线路卡和来电卡状态
6. 挂断

预期结果：

- 来电卡显示紧急样式
- 有紧急告警或紧急来电提示
- 接通后不再继续维持未接听告警态
- 来电卡或线路卡出现 `接通后录音` 或 `录音中`
- 结束后急呼状态清理干净

重点证据：

- 接听前截图
- 接听后显示 `录音中` 的截图

### S03 急呼主叫发起

前置条件：

- 网页端可主动发起急呼

执行步骤：

1. 在网页端选择急呼目标分机
2. 发起急呼
3. 等待目标接听
4. 观察线路卡状态变化
5. 挂断

预期结果：

- 网页端产生急呼呼出会话
- 目标接听后线路卡进入接通态
- 接通后线路卡出现 `录音中`
- 结束后录音态和占用态清理干净

重点证据：

- 发起后线路卡截图
- 接通后 `录音中` 截图

### S04 人工中继

前置条件：

- 外线 / 中继来电可落到调度员网页

执行步骤：

1. 触发一通人工中继来电
2. 观察来电卡是否显示“人工中继”
3. 点击应答
4. 输入或选择桥接目标
5. 完成桥接
6. 检查 UI 是否同步清理

预期结果：

- 来电卡明确区分人工中继
- 可手动应答
- 桥接成功后，中继临时提示不残留
- 线路卡状态与实际桥接结果一致

### S05 自动中继

前置条件：

- 自动中继模式已开启

执行步骤：

1. 开启自动中继模式
2. 触发一通自动中继来电
3. 在自动中继提示中输入目标号码
4. 点击转接
5. 观察结果

预期结果：

- 来电卡明确显示“自动中继”
- 页面出现目标输入框和转接按钮
- 转接成功后 UI 清理正常
- 不应误显示为普通来电

### S06 盲转来电

前置条件：

- 可构造盲转到调度员的来电

执行步骤：

1. 构造盲转场景，让调度员收到来电
2. 观察来电卡元数据
3. 接听或拒绝

预期结果：

- 来电卡显示转接专属样式
- 页面可见转接来源 / 目标等元数据
- 不应退化成普通来电文案

### S07 咨询转接来电

前置条件：

- 可构造咨询转接到调度员的来电

执行步骤：

1. 构造咨询转接场景
2. 观察来电卡和线路卡
3. 接听或拒绝

预期结果：

- 来电卡显示“咨询转接”或咨询支路相关文案
- 原主叫 / 转接来源信息可见
- 线路卡场景标签正确

### S08 监听

前置条件：

- 分机 `B` 与 `C` 已建立稳定通话
- 调度员可从线卡或对象状态卡发起监听

执行步骤：

1. 让 `B` 与 `C` 建立通话
2. 在网页端从线卡或对象状态卡点击 `监听`
3. 观察是否自动接入监听支路
4. 观察来电卡 / 线路卡显示
5. 挂断监听腿

预期结果：

- 无需再手工点“接听”才能进入监听
- 线路卡显示监听场景
- 来电卡或线路卡出现 `监听中`
- 强拆按钮可见
- 结束监听后监控态清理干净

重点证据：

- 点击监听后是否自动接入
- `监听中` 状态截图

### S09 强插

前置条件：

- 分机 `B` 与 `C` 已建立稳定通话

执行步骤：

1. 在网页端点击 `强插`
2. 观察是否自动接入
3. 确认调度员可加入通话
4. 观察来电卡 / 线路卡状态

预期结果：

- 强插腿自动接入
- 线路卡场景显示为强插支路
- 页面出现 `强插中`
- 被监控对象和调度员线路状态一致

重点证据：

- 强插后线路卡截图
- 监控对象信息截图

### S10 强拆

前置条件：

- 已完成一次监听或强插

执行步骤：

1. 在监听或强插场景下点击 `强拆`
2. 观察接口返回和页面变化
3. 检查目标双方是否释放
4. 如果是强插场景，检查会议腿是否也被清掉

预期结果：

- `force_release_call` 返回成功
- 页面线路卡消失或变成结束态
- 被监控双方释放
- 强插场景下不应残留会议腿

重点证据：

- 接口返回
- 强拆前后 `show channels as json` 对比

### S11 对象状态面板

前置条件：

- 网页端已注册

执行步骤：

1. 打开“用户 / 中继状态”面板
2. 观察首帧加载和更新时间
3. 让某分机进入空闲 / 振铃 / 通话 / 离线几种状态
4. 让中继进入空闲 / 振铃 / 占用或不可用状态
5. 点击刷新状态

预期结果：

- 面板能显示用户和中继分区
- 汇总数与实际状态变化一致
- 用户卡片可见注册态 / 忙闲态 / 当前通话
- 对象卡片上的监听 / 强插 / 强拆入口可用

### S12 录音态显示

前置条件：

- 可触发急呼录音

执行步骤：

1. 执行 `S02` 或 `S03`
2. 在急呼接通后观察线路卡
3. 如仍保留来电卡，观察来电卡状态标签
4. 挂断后观察状态是否清理

预期结果：

- 页面出现 `录音中` 或 `接通后录音`
- 不再是“后台已经录音，但页面完全不可见”
- 通话结束后录音标签被清理

## 7. 当前已知高风险点

联调时优先注意以下问题：

1. 监听 / 强插自动接入已统一切到主链路，需重点验证浏览器自动播放限制是否会影响现场结果。
2. 强插后的强拆已补了 `conference_name` 扩展清理，需重点验证现场 `show channels as json` 的通道字段是否稳定带出会议名。
3. 录音态当前仍以急呼录音链路为主，普通会话录音是否要统一展示需要现场口径确认。
4. 扬声态仍缺少可靠的会话级数据源，如果现场要求纳入统一状态展示，需要追加设计。
5. 若现场仍出现监控相关旧 `exec.php` 路径，说明部署版本不是当前工作区代码或存在缓存未刷新。

## 8. 执行结论口径

本清单执行完成后，建议按下面口径汇总：

- `通过`：页面结果、接口结果、实际通话行为一致
- `失败`：功能未达预期，且可稳定复现
- `阻塞`：前置环境未满足，无法完成验证

不要只写“功能看起来正常”，必须至少写清：

- 哪个场景
- 哪一步
- 页面看到什么
- 实际行为是什么
- 证据在哪里
