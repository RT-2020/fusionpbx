# MT-T1115 新版 WebRTC 场景完成度核对

## 1. 范围和结论

本文只分析新版 WebRTC 调度路径，不再把旧版 FusionPBX Operator Panel 计入完成度。

分析范围：

- `app/basic_operator_panel/resources/jssip-client.js`
- `app/basic_operator_panel/resources/dispatcher-control.js`
- `app/basic_operator_panel/dispatcher_api.php`
- `app/basic_operator_panel/index.php`
- `app/basic_operator_panel/resources/dispatcher.css`

当前结论：

- 新版已经从“只有普通来电/急呼”的粗粒度实现，推进到了“按场景识别和渲染”的阶段。
- 标准条款里“不同呼叫有不同声、光提示及号码显示”这部分，已经基本具备框架和主要链路。
- 但标准条款里更难的“用户或中继状态指示、用户状态明了”仍然没有真正完成。当前页面清楚的是“会话状态”，不是“用户/中继对象状态”。
- 监听、强插、强拆已经进入新版主链路，但还存在两个明显收尾点：
  1. 监听链路默认不是自动接入，便利性不如强插。
  2. 强插后的强拆主要拆原始双方，不一定同时清理调度员自己的会议腿。

综合判断：

- 就 `5.5.3.8` 这条标准而言，新版当前完成度可评估为 `60% ~ 70%`。
- 如果单看“场景识别 + 差异化提示 + 号码显示”，完成度约 `75% ~ 85%`。
- 如果看“用户/中继状态指示 + 调度员监控便利性闭环”，完成度约 `35% ~ 50%`。

## 3. 对 `5.5.3.8` 的逐项对照

标准原文要点可以拆成 4 部分：

1. 调度终端应具有用户或中继的状态指示。
2. 用户对调度终端的各种呼叫均可通过不同的声、光提示及号码显示。
3. 用户状态明了。
4. 调度员可方便地运用强插、强拆等功能实施监控。

## 5. 为什么说现在清楚的是“会话状态”，不是“用户/中继状态”

### 5.1 会话状态这部分已经比较清楚

当前新版已经能把以下信息稳定挂到 `session` 上：

- `scene`
- `callType`
- `entityType`
- `sessionState`
- `displayNumber`
- `displayName`
- `transferMeta`
- `trunkMeta`
- `monitorMeta`

代码证据：

- `jssip-client.js:277-310`
- `jssip-client.js:320-419`
- `jssip-client.js:451-472`

这意味着当前页面已经能清楚表达：

- 这是一通什么类型的会话。
- 当前是在振铃、接通、保持还是转接。
- 来电号码、名称、转接来源、监控对象是谁。

### 5.2 用户/中继对象状态这部分仍然缺层

当前缺的是“对象状态聚合层”，例如：

- 分机 `8001` 当前是空闲、振铃、通话中、保持、离线，还是被监听。
- 中继 `trunk-A` 当前是空闲、占用、振铃、故障。

现在没有这一层的直接证据：

- `dispatcher_api.php:812-833` 的 `get_extensions` 只返回分机静态信息，没有运行态字段。
- `dispatcher-control.js:315-389` 和 `dispatcher_api.php:1041-1085` 只是在维护“调度员浏览器在线心跳”，不是在维护“所有分机/中继状态”。
- `dispatcher-control.js:1154-1237` 的线卡只展示当前活跃会话，且最多取前 6 路。

所以当前新版更准确的定义是：

- 已经接近“多场景会话调度台”。
- 还不是“标准意义上的用户/中继状态监控台”。

### 6.2 还没彻底闭环的部分

| 问题 | 现状 | 影响 |
| --- | --- | --- |
| 监听便利性不够 | 监听模式没有像强插一样配置自动接入 | 调度员发起监听后，通常还需要人工接听 |
| 强拆范围不完整 | `force_release_call` 主要处理 `target_uuid` 和 `bridge_uuid` | 强插场景下，调度员自己的会议腿不一定同步清掉 |
| 模式切换存在瞬断 | `switchMonitorMode` 先挂当前腿，再发新模式请求 | 如果新请求失败，调度员会失去原监控腿 |
| 仍保留旧链路兜底 | `index.php` 在新 API 失败时仍会 fallback 到旧命令 URL | 说明新链路已成主链，但还不是完全独立 |

## 8. 建议的下一步优先级

### 8.1 P0：补用户/中继状态面板

目标：

- 从“会话面板”升级到“对象状态面板”。

需要补的内容：

- 新增一个状态聚合 API，返回：
  - 分机号
  - 显示名
  - 对象类型 `user/trunk`
  - 当前对象状态 `offline/idle/ringing/busy/held/monitoring`
  - 关联会话 ID / 通道 UUID
- 页面新增固定的“用户/中继状态列表”或“状态卡片区”。

### 8.2 P0：把中继识别从“前端猜测”升级到“服务端明确标记”

目标：

- 减少对号码规则、显示名关键字的依赖。

建议：

- 服务端在中继来电进入 WebRTC 调度端前，明确写入 `X-Trunk-Call`、`X-Trunk-Mode`、`X-Call-Scene`。
- 转接场景也尽量补全 `X-Call-Scene`，不要只靠 `Refer-To/Replaces/History-Info` 猜。

### 8.3 P1：补监控收尾

目标：

- 让监听、强插、强拆真正达到“方便实施监控”。

建议：

- 监听模式增加自动接入能力，减少人工接听步骤。
- 强拆接口增加对 `conference_name` 或调度员监控腿 UUID 的处理，确保强插后能一次性拆净。
- 模式切换改为“新腿建立成功后再释放旧腿”，避免瞬断。

## 9. 最终判断

新版当前已经不再是“只有基础通话”的状态，而是已经具备：

- 统一场景识别
- 差异化声光提示
- 差异化号码与元数据展示
- 新版监听/强插/强拆 API 主链路

但离标准条款完全达标，还差最后一层最关键的能力：

- 不是再补更多“会话按钮”。
- 而是补“用户/中继对象状态层”和“监控闭环收尾”。

换句话说：

- 新版现在已经基本解决了“各种呼叫怎么区分显示”的问题。
- 还没有真正解决“用户和中继状态如何一眼看清”的问题。
