# MT-T1115 新老实现冲突与保留建议

## 1. 结论先行

不建议继续把“旧版 FusionPBX Operator Panel 实现”和“新版 WebRTC 调度实现”并行当作两套同级主线长期维护。

建议方案：

- 保留新版 WebRTC 调度实现作为主线继续完成需求。
- 保留旧版 FusionPBX Operator Panel 的状态采集逻辑、成熟监控语义和部分控制能力，作为迁移参考和过渡期兜底。
- 不建议继续在旧版 UI 上扩展新需求，也不建议让两套 UI 在同一业务层面长期并行演进。

一句话判断：

- 主线应该留新版。
- 旧版不应该继续作为主产品交互面继续扩展，而应该降级为“参考实现 / 兼容监控页 / 管理员兜底页”。

## 2. 先定义新老两版分别是什么

### 2.1 旧版

这里的“老版”本质上是 FusionPBX `Operator Panel` 风格实现，核心链路是：

- `app/basic_operator_panel/index.php`
- `app/basic_operator_panel/resources/content.php`
- `app/basic_operator_panel/resources/classes/basic_operator_panel.php`
- `app/basic_operator_panel/exec.php`

它的特点是：

- 通过轮询 `content.php` 刷新状态块
- 通过 `show channels as json + uuid_dump` 获取交换机侧状态
- 通过 `exec.php` 发起 `originate / uuid_kill / transfer / eavesdrop` 这类交换机控制

### 2.2 新版

这里的“新版”是你们后来叠加的 WebRTC 网页调度实现，核心链路是：

- `app/basic_operator_panel/resources/jssip-client.js`
- `app/basic_operator_panel/resources/dispatcher-control.js`
- `app/basic_operator_panel/dispatcher_api.php`

它的特点是：

- 浏览器直接作为 SIP/WebRTC 终端注册
- 自己维护 session、来电弹窗、线路卡片
- 支持组呼、全呼、会议、急呼、浏览器接听/挂断/保持/转接

## 3. 新老实现的根本差异

| 维度 | 旧版 FusionPBX 实现 | 新版 WebRTC 实现 | 本质差异 |
| --- | --- | --- | --- |
| 状态来源 | FreeSWITCH 通道状态 | 浏览器 JsSIP session 状态 | 一个是交换机视角，一个是浏览器终端视角 |
| 交互方式 | 刷新式看板 | 实时会话控制面板 | 一个偏监控台，一个偏软终端 |
| 呼叫发起方式 | `exec.php` 下发 `originate/uuid_*` | `sipClient.makeCall()/transfer()/acceptById()` | 一个是交换机代打，一个是浏览器直接通话 |
| 转接语义 | UUID 级控制 | SIP REFER / session 级控制 | 并不是同一种转接模型 |
| 监听/强插 | 旧版已有成熟入口 | 新版只部分接入 | 旧版偏监控，新版偏终端 |
| 急呼 | 后补，较弱 | 当前最完整 | 新版明显更强 |
| 组呼/会议 | 原生较弱 | 当前已成型 | 新版明显更强 |
| 可维护性 | PHP 渲染和轮询耦合较重 | 前端控制逻辑集中在 JS | 新版更适合继续产品化 |

## 4. 实际代码里的冲突点

## 4.1 同一页面同时挂了两套实现

代码证据：

- [index.php](D:\Project\Project\博创\fusionpbx\fusionpbx\app\basic_operator_panel\index.php#L337)  
  旧版仍然轮询 `resources/content.php`
- [index.php](D:\Project\Project\博创\fusionpbx\fusionpbx\app\basic_operator_panel\index.php#L310) 到 [index.php](D:\Project\Project\博创\fusionpbx\fusionpbx\app\basic_operator_panel\index.php#L315)  
  同页又加载了 `jssip-client.js / dispatcher-control.js / emergency-audio.js`
- [index.php](D:\Project\Project\博创\fusionpbx\fusionpbx\app\basic_operator_panel\index.php#L1686)  
  同页初始化 `new DispatcherControl()`

冲突本质：

- 旧版在轮询刷新整个监控看板。
- 新版在同页维护浏览器 SIP 会话和自己的 UI 状态。
- 这意味着同一页面同时存在两个状态机。

问题：

- 任何需求分析、调试、验收，都会首先遇到“到底哪个状态才是主状态”的问题。

## 4.2 同一业务有两种发起方式

旧版方式：

- [index.php](D:\Project\Project\博创\fusionpbx\fusionpbx\app\basic_operator_panel\index.php#L460) 到 [index.php](D:\Project\Project\博创\fusionpbx\fusionpbx\app\basic_operator_panel\index.php#L469)  
  拖拽后走 `get_transfer_cmd()` 或 `get_originate_cmd()`
- [index.php](D:\Project\Project\博创\fusionpbx\fusionpbx\app\basic_operator_panel\index.php#L490) 到 [index.php](D:\Project\Project\博创\fusionpbx\fusionpbx\app\basic_operator_panel\index.php#L501)  
  输入号码后走 `send_cmd()`
- [index.php](D:\Project\Project\博创\fusionpbx\fusionpbx\app\basic_operator_panel\index.php#L625)  
  `call_direct()` 也是走 `get_originate_cmd()`

新版方式：

- [index.php](D:\Project\Project\博创\fusionpbx\fusionpbx\app\basic_operator_panel\index.php#L2501) 到 [index.php](D:\Project\Project\博创\fusionpbx\fusionpbx\app\basic_operator_panel\index.php#L2528)  
  `callExtensionDirect()` 直接走 `dispatcherControl.sipClient.makeCall()`

冲突本质：

- 旧版是“交换机代替调度分机发起呼叫”。
- 新版是“浏览器注册成 SIP 分机自己发起呼叫”。

这不是 UI 差异，是控制模型差异。

影响：

- 呼叫归属不同
- 会话状态来源不同
- 后续转接、录音、计时、监控的语义都会不同

## 4.3 同一业务有两种转接模型

旧版转接：

- [dispatcher-utils.js](D:\Project\Project\博创\fusionpbx\fusionpbx\app\basic_operator_panel\resources\dispatcher-utils.js#L7)  
  生成 `exec.php?cmd=uuid_transfer...`
- [index.php](D:\Project\Project\博创\fusionpbx\fusionpbx\app\basic_operator_panel\index.php#L498)  
  `go_destination()` 使用 `get_transfer_cmd()`

新版转接：

- [dispatcher-control.js](D:\Project\Project\博创\fusionpbx\fusionpbx\app\basic_operator_panel\resources\dispatcher-control.js#L854) 到 [dispatcher-control.js](D:\Project\Project\博创\fusionpbx\fusionpbx\app\basic_operator_panel\resources\dispatcher-control.js#L887)  
  `transferLine()` 走 `sipClient.transfer()`
- [jssip-client.js](D:\Project\Project\博创\fusionpbx\fusionpbx\app\basic_operator_panel\resources\jssip-client.js#L1457)  
  底层是 `session.refer(target)`

冲突本质：

- 旧版是 UUID/交换机级转接。
- 新版是 SIP REFER/session 级转接。

问题：

- 页面上看起来都叫“转接”，但实际行为、成功条件、确认方式都不同。
- 这就是为什么现在“转接中”只能做成本地 UI 状态，而没法形成统一业务闭环。

- 维护成本会持续指数上升

## 5. 哪一版更适合作为主线

## 5.1 如果选旧版作为主线

优点：

- 监控能力成熟
- 上游 FusionPBX Operator Panel 语义清晰
- 用户状态、监听、插入讲话、强拆、转接等能力基础更扎实

缺点：

- 架构是轮询 + PHP 渲染块，不适合继续承载你们现在的 WebRTC 调度产品化需求
- 急呼、SIP 自动注册、浏览器接听、会议桥控制这些能力都主要在新版
- 如果回退到旧版主线，等于要把最近一轮在新版上投入的大部分工作重新搬回旧架构
- 旧版更适合作为“监控看板”，不适合作为“网页软终端 + 调度控制台”的唯一前端

结论：

- 不适合作为后续唯一主线

## 5.2 如果选新版作为主线

优点：

- 符合当前“网页调度终端”的产品方向
- 已经具备 SIP 自动注册、浏览器通话、组呼/全呼/会议、急呼、录音等近期投入成果
- 前端状态机和交互逻辑集中在 JS，后续补需求成本更可控

缺点：

- 监控/强插/强拆/中继这些标准核心能力还没补完整
- 还需要把旧版成熟的状态语义和动作能力迁移进来

结论：

- 更适合作为主线

## 6. 最终建议

## 6.1 保留哪一版

建议：

- 保留新版 WebRTC 调度实现作为唯一主线

原因：

1. 近期研发投入都在新版
2. 新版更符合“网页调度终端”而不是“传统监控看板”的方向
3. 急呼、组呼、全呼、会议、SIP 注册这些能力已经在新版成型
4. 如果改回旧版主线，等于倒退架构方向

## 6.2 旧版怎么处理

建议：

- 不删除旧版能力
- 但把旧版 UI 降级为：
  - 参考实现
  - 迁移期兜底页
  - 管理员监控/调试页

旧版应保留的内容：

- 状态聚合逻辑
- 用户状态映射逻辑
- 呼叫方向判断逻辑
- 成熟的监听/插入讲话/强拆/转接业务语义

旧版不建议继续扩展的内容：

- 新的主交互页面
- 新的业务入口
- 新的产品级功能

## 6.3 新版继续怎么做

建议路径：

1. 新版继续作为主 UI
2. 把旧版成熟的“监控语义”迁移到新版，而不是把新版功能回灌到旧版
3. 最终让旧版从“主业务页面”退到“兼容调试页”

## 7. 继续在新版上完成需求时，要迁移哪些东西

### 第一类：必须迁移

- 用户状态模型
- 中继状态模型
- 呼叫方向模型
- 监听 / 插入讲话 / 强拆动作语义
- 转接识别语义

### 第二类：必须重构

- `exec.php` 路由
- 新版来电场景分类
- 中继来电识别入口
- 不同呼叫的提示矩阵

### 第三类：不再双写

以下能力不应该再在新老两套 UI 中同时独立扩展：

- 呼叫发起
- 转接
- 中继处理
- 监听
- 强插
- 强拆
- 录音状态展示

## 8. 一句话落地建议

如果你要做产品级收口，最合理的路线是：

- 以新版 WebRTC 调度实现为唯一主线继续补需求；
- 以旧版 FusionPBX Operator Panel 为能力参考和过渡期兜底；
- 尽快消除同页双状态机、双控制链路、双 DOM 容器、双呼叫模型的冲突。
