# MT-T1115 网页调度终端统一实施方案与执行评估

## 1. 文档目的

本方案用于在不牺牲现有已落地能力的前提下，完成 MT-T1115 网页调度终端需求收口，并明确：

- 什么功能必须完成才算满足需求
- 当前代码真实做到哪一步
- Web、PHP、FreeSWITCH、Lua 各自承担什么职责
- 应该按什么顺序实施，才能避免返工和链路分叉
- 在什么条件下才允许进入“已完成”状态

本方案明确采用：

- `Web / PHP / ESL` 作为主控链路
- `FreeSWITCH` 负责原子能力执行
- `Lua` 只补交换机侧最小钩子，不承担网页调度主业务

## 2. 目标与硬性约束

### 2.1 最终目标

网页调度终端需要完成以下能力闭环：

- 普通呼叫、紧急呼叫、中继、转接、监听、强插、会议/组呼的统一场景识别
- 用户、中继、当前处理会话、等待会话、被监控会话的页面可见状态
- 普通、紧急、中继、转接、监控、会议邀请的差异化声光提示
- 调度控制动作闭环：
  - 接听
  - 挂断
  - 保留
  - 恢复
  - 监听
  - 强插
  - 强拆
  - 人工接续
  - 中继汇接
  - 全呼
  - 组呼
  - 会议控制
- 默认全量录音：
  - 普通
  - 中继
  - 转接
  - 监听
  - 强插
  - 会议/组呼
  - 紧急呼叫
- 页面上可见录音状态
- 页面上可见扬声通话状态
- 多路并发呼叫互不覆盖

### 2.2 不允许的做法

- 不再继续把新需求叠加到旧 `exec.php` 混杂分支
- 不再同时维护“旧 Operator Panel 路径”和“新版 WebRTC 路径”两套主业务逻辑
- 不把网页调度主流程整体重写成 `Lua + dialplan` 主导
- 不在没有真实 FreeSWITCH 联调证据时声明“完成”

## 3. 当前实现现状评估

## 3.1 已有基础能力

当前工作区已经具备以下基础：

- 新版 WebRTC 页面已形成统一场景模型主干：
  - `app/basic_operator_panel/resources/jssip-client.js`
  - `app/basic_operator_panel/resources/dispatcher-control.js`
- 监听、强插、强拆主路径已收口到：
  - `app/basic_operator_panel/dispatcher_api.php`
- 会议/组呼/邀请/结束会议主路径已收口到：
  - `app/basic_operator_panel/dispatcher_conference_api.php`
- 普通通话和紧急通话的录音能力已能通过 FreeSWITCH 命令层投入
- 当前页面已经能显示：
  - 录音态
  - 监听态
  - 强插态
  - 中继/转接/急呼/会议等场景标签

## 3.2 当前未收口项

从代码实际看，仍有以下未闭环点：

### A. FreeSWITCH 主链未统一抽象

当前 `event_socket::api()` 调用分散在：

- `app/basic_operator_panel/dispatcher_api.php`
- `app/basic_operator_panel/dispatcher_conference_api.php`
- `app/basic_operator_panel/exec.php`

问题：

- 同类动作缺少统一封装
- 错误处理、日志、结果判定不一致
- 录音、监控、会议相关命令分散维护

### B. 旧 `exec.php` 仍有历史混杂逻辑

`app/basic_operator_panel/exec.php` 里：

- `originate` 路径仍承担旧页面兼容
- `uuid_record` 分支内部仍混杂旧监听/三方通话残留

问题：

- 容易形成“双主线”
- 后续补需求时继续污染旧链路
- 影响后端闭环判断

### C. FreeSWITCH / Lua 层没有形成“basic_operator_panel 专属资产”

当前仓库中：

- 存在 FusionPBX 通用脚本，如：
  - `app/switch/resources/scripts/eavesdrop.lua`
  - `app/switch/resources/scripts/three_way.lua`
  - `app/switch/resources/scripts/app/conference_center/resources/scripts/start_recording.lua`
- 但 `app/basic_operator_panel` 下没有独立 Lua 或独立 switch 配置文件

这说明：

- 当前是 PHP 直接控 FreeSWITCH
- 不是“basic_operator_panel 已补全自己的 Lua / dialplan 资产”

### D. 扬声通话状态没有可靠统一数据源

当前录音态和监控态已可上屏，但“扬声态”仍没有统一、稳定、会话级数据源。

### E. 没有真实环境下的完整验收证据

目前缺的是现场联调证据，而不是单纯代码入口：

- 浏览器 WebRTC
- FreeSWITCH 会话建立
- 中继/转接/会议实际通话
- 录音文件落盘
- 强拆/强插会议腿释放

## 3.3 当前总体判断

当前状态不是“从零开始”，也不是“已经完成”。更准确的判断是：

- 主业务前后端链路已经成型
- 功能收口的关键风险集中在：
  - 后端链路统一
  - 旧路径清理
  - 扬声态数据源
  - 真实环境联调

结论：

**项目具备继续实施条件，但必须先做后端收口和执行门槛约束，再进入功能补全与联调。**

## 4. 推荐架构方案

## 4.1 分层职责

### 第一层：Web UI / 状态机层

文件：

- `app/basic_operator_panel/resources/jssip-client.js`
- `app/basic_operator_panel/resources/dispatcher-control.js`
- `app/basic_operator_panel/index.php`

职责：

- 场景识别
- 会话状态管理
- UI 渲染
- 按钮动作发起
- 页面提示音/视觉提示

不承担：

- 业务最终裁决
- 交换机原子动作实现

### 第二层：PHP 调度编排层

文件：

- `app/basic_operator_panel/dispatcher_api.php`
- `app/basic_operator_panel/dispatcher_conference_api.php`
- 新增统一 service 类

职责：

- 权限校验
- 参数清洗
- 目标通道解析
- 命令编排
- 交换机结果判定
- 结构化 JSON 返回

### 第三层：FreeSWITCH 原子能力层

职责：

- `originate`
- `uuid_transfer`
- `uuid_bridge`
- `uuid_kill`
- `uuid_record`
- `conference record`
- channel variables
- SIP headers

原则：

- 只做原子动作
- 不承载页面场景逻辑

### 第四层：Lua 最小钩子层

职责限定为：

- 会议录音后处理
- 通话录音后处理
- 应急兜底通知/日志
- 交换机内生异步任务

不做：

- 页面场景编排
- 网页按钮业务主链

## 4.2 推荐收口原则

- 监听、强插、强拆统一走 `dispatcher_api.php`
- 会议、组呼、邀请、结束会议统一走 `dispatcher_conference_api.php`
- `exec.php` 只保留旧入口兼容，不再扩展新能力
- 新增 `Switch Service` 统一封装所有 ESL 命令

## 5. 详细实施方案

## 5.1 阶段 P0：基线冻结与收口边界确认

### 目标

为后续实施建立唯一基线，避免边改边漂移。

### 任务

- 冻结本次需求基线，以 `docs/MT-T1115网页调度终端需求总结-2026-03-21.md` 为主需求依据
- 以新版 WebRTC 路径作为唯一主产品路径
- 明确旧 `exec.php` 仅保留兼容，不新增业务能力
- 明确“Lua 仅补钩子，不承载主流程”

### 交付物

- 本方案文档
- 后续开发任务清单修订版

### 通过标准

- 不再出现“新功能到底加到哪条链路”的歧义

## 5.2 阶段 P1：统一后端 Switch Service

### 目标

把分散在多个 PHP 文件中的 FreeSWITCH 操作统一封装。

### 任务

- 新增统一 service，例如：
  - `app/basic_operator_panel/resources/classes/operator_panel_switch_service.php`
- 统一封装以下动作：
  - 发起普通呼叫
  - 发起紧急呼叫
  - 发起监听
  - 发起强插
  - 强拆
  - 查询通道
  - 桥接
  - 转移到会议
  - 启动通话录音
  - 启动会议录音
  - 查询通道 UUID
- 统一 ESL 成功判定和错误返回
- 统一日志上下文字段

### 涉及文件

- 新增 service 类
- `dispatcher_api.php`
- `dispatcher_conference_api.php`
- `exec.php`

### 通过标准

- `dispatcher_api.php` 和 `dispatcher_conference_api.php` 中的 FreeSWITCH 命令不再散落手写
- 所有动作的成功/失败返回格式统一

## 5.3 阶段 P2：录音策略统一收口

### 目标

保证“默认全部通话录音”在命令层和状态层都闭环。

### 任务

- 统一定义录音策略：
  - 普通通话：`uuid_record` 或建链时 `api_on_answer`
  - 紧急通话：建链即自动录音
  - 监听/强插：监控建链即录音
  - 中继/转接：建链即录音
  - 会议/组呼：`conference record`
- 统一“页面状态”和“后端录音投入”的关系：
  - 页面状态只展示，不是唯一真源
- 为录音失败提供明确错误回写和日志
- 明确录音文件命名规范和落盘目录规范

### 通过标准

- 所有通话类型都有明确的录音投入机制
- 不存在“页面显示录音中但后端没录”的无证据状态
- 不存在会议类双录或重复录音冲突

## 5.4 阶段 P3：监控和中继能力最终收口

### 目标

把标准要求的监听、强插、强拆、中继汇接、人工中继、自动中继全部落成单一主路径。

### 任务

- 监听主路径只保留 `dispatcher_api.php -> monitor_call`
- 强插主路径只保留 `dispatcher_api.php -> monitor_call`
- 强拆主路径只保留 `dispatcher_api.php -> force_release_call`
- 中继人工应答 / 自动中继只保留新版 WebRTC UI 路径
- 对中继保留、恢复、回切的状态回写做完整闭环

### 通过标准

- 页面入口只有一套主路径
- 不再依赖旧页面 fallback
- 中继场景与普通场景的提示、状态、操作全部区分清楚

## 5.5 阶段 P4：扬声通话能力补齐

### 目标

补齐标准中的“扬声通话和通话录音功能”。

### 关键前置判断

必须先明确“扬声通话”在当前产品里的落地语义：

- 是浏览器侧扬声器输出设备选择
- 还是某类广播/外放通话模式
- 还是中继/组呼中的免提外放状态

### 任务

- 先完成语义确认
- 再决定数据源：
  - 浏览器侧设备状态
  - FreeSWITCH channel var
  - 后端会话标记
- 页面加入统一“扬声态”显示

### 通过标准

- 扬声态有唯一可信数据源
- 页面上可见
- 联调时可验证

## 5.6 阶段 P5：Lua 最小钩子补齐

### 目标

只补当前体系真正需要的 Lua，而不是另起一套主流程。

### 推荐仅补以下能力

- 录音完成后的后处理
  - 文件检查
  - 元数据记录
  - 可选回写数据库
- 应急兜底通知
  - 交换机侧事件触发
  - 可选告警后处理
- 会议录音后处理
  - 会后整理
  - 可选文件校验

### 不建议补的内容

- 监听/强插/强拆主流程 Lua 化
- 普通网页调度场景 Lua 化
- 再建一套 basic_operator_panel 专属复杂 dialplan

### 通过标准

- Lua 只做交换机内生补充，不与 PHP 主链争抢职责

## 5.7 阶段 P6：旧链路清理

### 目标

移除阻碍后续验收的历史分叉点。

### 任务

- 清理 `exec.php` 中监控相关历史混杂逻辑
- 只保留必要兼容动作
- 为旧入口增加显式注释，标明已废弃或兼容用途
- 清理无效 dialplan 删除逻辑等历史残留

### 通过标准

- 再读代码时能明确看出哪条是唯一主路径
- 没有“同一动作三套后端实现”的情况

## 5.8 阶段 P7：联调与验收

### 目标

把“代码看起来可以”转成“真实环境验收通过”。

### 必测场景

- 普通呼入
- 普通呼出
- 紧急单呼
- 紧急组呼/广播
- 监听
- 强插
- 强拆
- 转接
- 人工中继
- 自动中继
- 会议
- 组呼
- 录音落盘
- 会议录音落盘
- 扬声态
- 多路并发

### 每个场景必须记录

- 页面提示是否正确
- 页面状态是否正确
- FreeSWITCH 命令是否执行成功
- 录音文件是否生成
- 通道是否按预期释放
- 是否有异常日志

### 通过标准

- 有联调记录
- 有问题回归记录
- 有最终验收结果表

## 6. 执行顺序与依赖关系

推荐顺序：

1. `P0` 基线冻结
2. `P1` Switch Service
3. `P2` 录音策略统一
4. `P3` 监控和中继收口
5. `P4` 扬声态语义确认与补齐
6. `P5` Lua 最小钩子
7. `P6` 旧链路清理
8. `P7` 联调验收

不推荐顺序：

- 先补 Lua
- 先补扬声 UI
- 先做大面积页面重构
- 在旧 `exec.php` 上继续叠需求

## 7. 风险评估

## 7.1 技术风险

### 风险 1：旧链路污染主链

表现：

- 同一动作在 `exec.php` 和 `dispatcher_api.php` 都能发起

影响：

- 联调结果不可控
- 问题难定位

处置：

- 先做后端收口，再做功能补齐

### 风险 2：录音策略不一致

表现：

- 页面显示录音中，但实际未录
- 会议类重复录音

影响：

- 验收失败

处置：

- 录音策略统一下沉到 switch 命令层

### 风险 3：扬声态语义不清

表现：

- 页面能显示但无法证明标准意义上的“扬声通话”

影响：

- 功能名义完成，验收不可证

处置：

- 先确认业务语义，再开发

### 风险 4：现场环境与工作区代码不一致

表现：

- 现场仍跑旧 JS 或旧 PHP

影响：

- 误判方案失效

处置：

- 执行前确认部署版本

## 7.2 管理风险

- 边改边补文档，导致基线漂移
- 未定义“完成标准”就进入联调
- 联调问题未回灌到方案和任务清单

## 8. 执行门槛

只有满足以下条件，才进入正式开发执行：

- 需求基线已冻结
- 主链路已确认
- 扬声通话语义已确认
- 允许逐步清理旧兼容路径

只有满足以下条件，才允许声明“已完成”：

- 代码主路径唯一
- 全量通话录音已验证
- 页面状态与后端行为一致
- 联调记录完整
- 关键场景都跑通

## 9. 评估结论

结论分为三层：

### 9.1 是否建议继续做

建议继续做。

原因：

- 现有工作区已经有足够基础，不需要推倒重来
- 当前问题集中且可收口
- 采用 `Web / PHP / ESL 主控` 路线最符合现有代码结构

### 9.2 是否建议改成 Lua 主导

不建议。

原因：

- 当前网页调度主路径已经成型
- Lua 只适合做交换机内生补充
- 改成 Lua 主导会引入第二套主业务系统

### 9.3 是否具备执行条件

具备，但要按本方案顺序执行，不能再零散补丁式推进。

最优执行入口为：

- 先做 `P1 + P2 + P3`
- 再处理 `P4`
- 再补 `P5`
- 最后联调验收
