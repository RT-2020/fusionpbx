# MT-T1115 网页调度终端现状差距清单

## 1. 文档目的

基于当前 `app/basic_operator_panel` 代码现状，按《MT-T1115-2011 多基站矿井移动通信系统通用技术条件》对网页调度终端进行差距分析，输出：

- 当前已具备的实现基础
- 当前未打通或存在风险的链路
- 与标准要求的主要差距
- 后续改造优先级

分析时间：

- `2026-03-21`

分析范围：

- `app/basic_operator_panel/index.php`
- `app/basic_operator_panel/resources/content.php`
- `app/basic_operator_panel/resources/classes/basic_operator_panel.php`
- `app/basic_operator_panel/resources/dispatcher-control.js`
- `app/basic_operator_panel/resources/jssip-client.js`
- `app/basic_operator_panel/resources/dispatcher-utils.js`
- `app/basic_operator_panel/resources/emergency-audio.js`
- `app/basic_operator_panel/dispatcher_api.php`
- `app/basic_operator_panel/exec.php`

## 2. 总体结论

当前代码不是一个“单一、统一语义”的网页调度终端，而是两套能力并存：

- 旧监控面板链路：
  `index.php -> resources/content.php -> resources/classes/basic_operator_panel.php -> exec.php`
- 新 WebRTC 调度链路：
  `jssip-client.js -> dispatcher-control.js -> dispatcher_api.php`

总体判断：

- 旧监控面板更接近标准中的“用户/中继状态指示、强插、强拆、监听、转接、录音”等监控调度要求。
- 新 WebRTC 调度链路更接近“网页调度终端”的形态，具备来电弹窗、线路卡片、紧急呼叫提示、组呼/全呼/会议等基础。
- 但两套链路之间没有统一的“呼叫场景模型、提示模型、监控动作模型”，因此当前整体状态仍是“部分满足”，尚不能认为已完整满足 `5.5.3.8` 和 `6.7.4.*` 的页面级要求。

核心结论：

- 标准中的“状态指示 + 各种呼叫差异化提示 + 号码显示 + 强插强拆监控”并未在当前网页端形成完整闭环。

## 3. 现状架构判断

### 3.1 旧监控面板链路

现状特征：

- `index.php:337-338` 通过轮询 `resources/content.php` 刷新状态块。
- `basic_operator_panel.php:160-216` 将 `show channels as json` 和 `uuid_dump` 合并进扩展状态数组。
- `content.php` 内已经实现：
  - 呼叫标识识别
  - 用户状态图标
  - 呼叫方向图标
  - 录音按钮
  - 监听
  - 插入讲话
  - 挂断单路/挂断双方
  - 转接输入框

判断：

- 旧链路在“看板式监控调度”上基础较强。
- 但其提示方式主要是静态刷新和图标，不等于标准所要求的完整“不同声、光提示”。

### 3.2 新 WebRTC 调度链路

现状特征：

- `jssip-client.js` 负责 JsSIP 注册、来电识别、会话管理。
- `dispatcher-control.js` 负责来电弹窗、线路卡片、保留、转接、紧急呼叫、组呼/全呼/会议、中继弹层等。
- `emergency-audio.js` 只实现了紧急呼叫的循环音频、语音播报和提示音。

判断：

- 新链路具备“网页调度终端”基础交互。
- 但对于普通来电、转接来电、中继来电、人工接续来电等场景，没有形成统一且可验证的差异化提示逻辑。

## 6. 主要差距与风险

### 6.1 来电场景识别过于粗糙

当前新面板的来电识别仅覆盖：

- `normal`
- `conference`
- `eavesdrop`
- `emergency`
- `three-way`

证据：

- `jssip-client.js:233-256`

问题：

- 未识别“转接来电”“人工接续来电”“人工中继”“自动中继”“咨询转接支路”“中继入局/出局”等业务场景。
- 未解析典型 SIP 转接头，例如：
  - `Referred-By`
  - `Refer-To`
  - `Replaces`
  - `History-Info`
  - `Diversion`

结果：

- 页面无法对“普通呼叫”和“转接类呼叫”做稳定区分。
- 页面无法对“中继呼叫”和“普通内部来电”做稳定区分。

### 6.2 差异化提示只覆盖紧急呼叫

当前不同声、光提示的实现基本只覆盖紧急呼叫：

- `emergency-audio.js:40-124`
  - 只有紧急告警服务。
- `dispatcher-control.js:586-610`
  - 仅判断是否紧急，然后统一进入普通来电队列。
- `dispatcher-control.js:1163-1189`
  - 普通来电卡片与转接来电、中继来电没有差异化样式和音效流程。

问题：

- 普通呼叫、转接来电、中继来电、人工接续来电没有独立声光策略。
- 当前不满足 `5.5.3.8` 所要求的“各种呼叫均可通过不同的声、光提示及号码显示”。

### 6.3 中继功能代码存在，但主流程未接入

当前中继相关页面和方法已经写出：

- `dispatcher-control.js:936-1118`
  - `handleTrunkIncomingCall`
  - `showManualTrunkPrompt`
  - `showAutoTrunkPrompt`
  - `acceptTrunkCall`
  - `bridgeTrunkCall`
  - `holdTrunkCall`
  - `processAutoTrunk`

但主来电入口：

- `dispatcher-control.js:558-610`
  - `onIncomingCall()` 中没有分流到 `handleTrunkIncomingCall()`

结果：

- 中继功能虽然“有代码”，但没有真正接入主场景识别链路。
- `6.7.4.6` 的人工中继/自动中继验收场景无法认为已经闭环。

### 6.4 新旧两套 UI 语义不统一

旧面板和新面板分别掌握不同能力：

- 旧面板擅长：
  - 用户状态
  - 呼叫方向
  - 监听/插入讲话/挂断双方/转接/录音
- 新面板擅长：
  - SIP 注册
  - 来电卡片
  - 线路卡片
  - 紧急呼叫专项
  - 组呼/全呼/会议

问题：

- 没有统一的“实体状态 + 通话状态 + 呼叫场景 + 调度动作”模型。
- 同一个业务在两套 UI 上的语义不同，容易导致标准映射不一致、联调困难、验收口径不一致。

### 6.5 监控控制后端路由存在高风险

前端构造的控制命令包括：

- `dispatcher-utils.js:8`
  - `uuid_transfer`
- `dispatcher-utils.js:13-15`
  - `uuid_eavesdrop`

但 `exec.php` 现状显示：

- 显式分支有 `originate`、`uuid_record`、`uuid_kill`、`uuid_exists`、`uuid_bridge`、`get_channel_uuid`
- 没有清晰、独立的 `uuid_transfer` 分支
- 没有清晰、独立的 `uuid_eavesdrop` 分支
- `exec.php:103-154` 中 `uuid_record` 分支内部混入了监听/插入讲话逻辑，并且直接使用：
  - `$chan_uuid`
  - `$ext`
  - `$destination`
  这些变量在该分支上方并未清晰赋值

判断：

- 这是当前最关键的实现风险之一。
- 页面按钮虽然存在，但后台执行路径有较大概率不稳定或存在隐性错误。

### 6.6 转接状态只是“发起者本地状态”，不是“来电场景识别”

当前新面板对“转接中”的处理：

- `dispatcher-control.js:777-779`
  - 线路卡片可显示 `转接中`
- `dispatcher-control.js:854-887`
  - `transferLine()` 在本地标记 `this.transferring[sessionId]`

问题：

- 这只表示“我发起了 REFER 转接”。
- 这不等于“系统能识别另一路来电属于转接来电”。

结果：

- 页面无法从接收端视角区分“普通来电”和“被转接进来的来电”。

### 6.7 中继/转接完成确认过弱

`dispatcher_api.php` 中的转接确认逻辑：

- `dispatcher_api.php:1040-1071`
  - `check_transfer` 仅检查目标分机是否存在 `ACTIVE` 通道

问题：

- 无法区分是普通接通、人工接续接通、转接完成、咨询转接完成还是其他通话。
- 不具备业务场景级确认能力。

## 7. 重点条款的逐项判断

### 7.1 对 `5.5.3.1` 的判断

有利因素：

- 旧面板已有监听、插入讲话、强拆、转接入口。
- 新面板已有线路级呼叫、保留、转接能力。

缺口：

- `exec.php` 控制路由有高风险。
- 新面板缺少“被监控中”场景的统一展示。

结论：

- `部分满足，高风险`

### 7.2 对 `5.5.3.2` 的判断

有利因素：

- 紧急头识别、优先卡片、音频提示、清警、抢占接听、录音都已有实现基础。

缺口：

- 仍是紧急专项实现，未与整体呼叫场景模型统一。
- 自动录音依赖 `get_channel_uuid -> uuid_record`，链路稳健性有待联调验证。

结论：

- `部分满足`

### 7.3 对 `5.5.3.6` 和 `6.7.4.6` 的判断

有利因素：

- 已写出人工中继、自动中继、桥接、保留等方法。

缺口：

- 主入口没有真正识别和分流中继呼叫。
- 中继忙时保留后继续处理的流程没有纳入统一线路状态机。

结论：

- `部分满足，未打通`

### 7.4 对 `5.5.3.8` 的判断

有利因素：

- 旧面板已有用户状态图标、方向图标、号码显示、监控操作入口。
- 新面板已有紧急呼叫专项提示。

缺口：

- 没有覆盖“各种呼叫”的差异化声光策略。
- 没有统一的用户/中继/转接/监控状态模型。
- 新面板无法稳定区分普通、转接、中继、人工接续等场景。

结论：

- `未完整满足`

## 8. 当前最优先处理的问题

优先级 `P0`：

- 修正 `exec.php` 控制路由，明确独立支持：
  - `uuid_transfer`
  - `uuid_eavesdrop`
  - `three-way / barge`
  - `hangup_both`

优先级 `P1`：

- 建立统一的呼叫场景模型，至少区分：
  - 普通来电
  - 紧急来电
  - 中继来电
  - 人工接续/人工中继来电
  - 自动中继来电
  - 转接来电
  - 监听支路
  - 插入讲话支路
  - 会议/组呼支路

优先级 `P1`：

- 在 `jssip-client.js` 中补转接相关 SIP 头识别。

优先级 `P1`：

- 在 `dispatcher-control.js` 中将 `queueIncomingCall()`、`renderLinesGrid()` 改为按 `scene` 渲染，而不是按 `isEmergency` 或 `_callType` 粗略处理。

优先级 `P2`：

- 将中继来电识别正式接入 `onIncomingCall()` 主流程。

优先级 `P2`：

- 补普通来电、中继来电、转接来电的独立提示音和视觉样式。

## 9. 结论摘要

当前代码不是“完全没有基础”，而是“能力分散、链路不统一、关键控制路由高风险”。

最接近标准的部分：

- 旧面板的状态显示和监控操作
- 新面板的紧急呼叫专项
- 新面板的组呼/全呼/会议能力

当前最不满足标准的部分：

- `5.5.3.8` 所要求的“各种呼叫差异化声光提示”
- 中继/转接场景的稳定识别与统一显示
- 强插/强拆控制链路的后端稳健性

最终判断：

- 当前实现可以认为“部分满足标准条款，有明显实现基础”，但不能认为“网页调度终端已完整满足 MT-T1115 调度终端要求”。
