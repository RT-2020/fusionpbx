# MT-T1115 新版 WebRTC 推进阶段确认与剩余任务

## 1. 结论

基于当前工作区代码和已有方案文档，MT-T1115 新版 WebRTC 改造已经明显超过“场景识别 / 提示矩阵 / 中继流程”阶段，当前更准确的定位是：

- 主体开发已推进到“监控主链路收口 + 对象级状态面板 + 会话状态标签”阶段
- 严格按任务清单验收口径看，当前更接近“阶段 5 待联调验收”的状态
- 如果按实施方案表的 5 阶段口径看，可判断为“阶段 4 已完成收口，阶段 5 已开始验收和剩余展示项处理”

- 监听 / 强插 / 强拆的代码主链路虽已收口，但还缺现场联调证明

## 4. 已经落地的核心内容

### 4.1 场景和统一状态模型

`resources/jssip-client.js` 已经具备统一 `scene` 映射和来电识别能力，能区分：

- 普通呼叫
- 急呼
- 人工 / 自动中继
- 盲转 / 咨询转接
- 监听支路
- 强插支路
- 会议支路

这说明“统一场景模型”已经不再停留在方案层，而是进入了实际主链路。

### 4.2 差异化提示和线路渲染

`resources/dispatcher-control.js` 已经通过 `getIncomingSceneConfig()`、`startScenePrompt()`、`queueIncomingCall()`、`renderLinesGrid()` 把不同场景的提示音、视觉标签、线路卡状态、可用按钮接到了新版 UI。

这部分对应实施方案表中的：

- 阶段 1
- 阶段 2

### 4.3 中继主流程

新版前端已经有人工中继、自动中继的来电提示、应答和桥接逻辑；现有代码说明中继已经不是旧版兼容角落逻辑，而是新版页面中的明确场景分支。

这部分对应实施方案表中的：

- 阶段 3

### 4.4 对象级状态总览面板

`dispatcher_api.php` 已新增 `get_entity_status_snapshot`，前端新增“用户 / 中继状态”面板，并支持自动刷新、告警显示、对象级监控入口。

这意味着当前版本已经从“只看会话状态”推进到“可看对象状态”，这是 2026-03-21 晚些时候代码推进的关键变化。

### 4.5 监控闭环与控制路由收口

当前工作区里，监控相关收口已经补到位：

- `dispatcher-control.js` 已通过 `prepareMonitorAutoAnswer()` + `tryAutoAnswerIncoming()` 串通监听 / 强插自动接入
- `dispatcher_api.php` 的 `force_release_call` 已支持按 `conference_name` 扩展清理会议腿
- `index.php` 中监听、强插、强拆的页面入口已统一走 `dispatcherControl.requestMonitorCall()` / `forceReleaseCall()`，不再保留监控相关旧 `exec.php` 回退主路径

这说明 `T6` / `T7` 在当前工作区代码里已经不再是“开发未完成”，而是“待现场验证”的状态。

## 5. 当前未收口的关键问题

### 5.1 扬声态仍无可靠会话级数据源

当前代码已经把以下状态补到了来电卡和线路卡：

- `录音中`
- `接通后录音`
- `监听中`
- `强插中`

但“扬声态”仍没有可靠的会话级来源。当前前端只能稳定拿到浏览器侧全局音频输出配置，不能直接还原到某一条会话或某一个实体状态。

因此 `T8` 目前更准确的结论是：

- 录音态和监控态展示已经补上
- 扬声态若必须纳入方案，需要补新的数据源或明确降级范围

### 5.2 联调与验收用例已落地文档，但尚未完成现场执行

目前已经形成新版 WebRTC 的联调验收清单文档，但还没有看到正式的逐场景执行结果回填。

`T10` 要求的是：

- 每个场景都有手工验证步骤
- 每个场景都有页面可见结果

因此 `T10` 当前更准确的状态是：

- 联调清单文档已落地
- 现场联调执行结果未落地
- 还不能视为验收完成

### 5.3 现场部署一致性仍需核验

当前工作区已经完成监控主链路收口，但本次终端里没有可直接联调的浏览器 + FreeSWITCH 现场环境，也没有看到生产站点部署结果。

因此还需要在真实环境里核验两件事：

- 部署版本是否已经包含当前工作区的监控收口代码
- 现场行为是否与当前代码意图一致，而不是仍然跑在旧缓存或旧脚本上
